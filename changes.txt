## Day 3 — 2026-09-04/05 — Phase 3: Products + Courses CRUD, storefront save fix

### Storefront save fix (why "save doesn't work")
- Root cause: the storefront builder saved via `upsert(..., { onConflict: "creator_id" })`, but the base schema has **no unique constraint on `storefronts.creator_id`** — Postgres rejects that with "no unique or exclusion constraint matching the ON CONFLICT specification". (Live diagnostics confirmed the project's schema drifted from local files, so the live state couldn't be trusted; the client no longer depends on either state.)
- Fix in `app/dashboard/storefront/page.tsx`: save now branches on the already-loaded row id — update by primary key when a storefront row exists, otherwise insert and keep the returned id. No ON CONFLICT anywhere. (Brand Kit's `onConflict: "user_id"` is fine — `creators.user_id` is unique.)
- Error handling improved: the save error text is shown in full (no truncation) and also logged to the console, so any future RLS/DB error is visible and paste-able. Save button is enabled for a never-saved storefront even before edits.

### Live diagnostics (no credentials were available for these earlier)
- `.env` now exists in the checkout, so the live project was probed (read-only + scratch rows, all cleaned up):
  - Service-role reads do **not** bypass RLS on this project: `creators` selects return no rows (its policy is a simple `auth.uid() = user_id` filter, and the service role has no auth user — table emptiness could NOT be confirmed), while `storefronts`/`landing_pages`/`products`/`courses`/`subscribers` selects fail with "permission denied for function is_own_creator". The live project is hardened with `is_own_*` helper functions that the service role lacks EXECUTE on.
  - **Anonymous reads on public pages are broken live**: all policies on a table are evaluated for the querying role, and the helper-based creator policies aren't granted to `anon` — so even "published readable by anyone" rows return `401 permission denied for function is_own_creator` for anon on `storefronts`/`landing_pages`/`products`/`courses`.
  - **Creator writes fail the same way for authenticated users** — confirmed by the reported storefront save error "permission denied for function is_own_creator": the INSERT/UPDATE/DELETE policies call `is_own_creator` and the `authenticated` role lacks EXECUTE on it. Reading an empty storefront slips through (no rows → policy function never evaluated), which is why the failure only surfaced on Save.
  - `public_creator_profiles` (Phase 2 migration) does not exist yet on the live project.
  - Auth signups were rate-limited and admin user creation refused during the session, so a full live RLS write test couldn't be run. **Live verification of the fix is still pending:** apply the migrations, then save the storefront and report any remaining error (now shown in full).

Fixes the anon public-read 401s AND the authenticated save/write "permission denied for function is_own_creator" errors. Idempotent (drop-all + recreate), so the file can simply be re-run. ## Day 6 addendum — Brand-kit "won't save in production" fixed

### Root cause
The brand-kit page had a silent dead-end, not a database problem (verified live:
a session-governed upsert against the production DB succeeds, count=1):
- When the initial `creators` load failed (expired token, network hiccup) or
  returned no row, `initial` stayed "" → `dirty` was permanently false → the
  Save button was permanently disabled with zero feedback. Every later click
  did nothing, which reads exactly as "it doesn't save in production".
- Load errors were never rendered (the error chip only showed after a failed
  save), so the trigger was invisible.

### Fixes (app/dashboard/brand-kit/page.tsx)
- Save is no longer gated on `dirty` — always clickable; upsert stays idempotent.
- `initial` uses a tri-state: null = row never loaded → edits still count as
  dirty and Save creates the creator row (first save = create).
- Load failures now surface immediately in the header (error chip + Retry save).
- Save shows the precise failure: session errors, handle collisions
  ("duplicate key ... creators_handle_key"), RLS denials — no more silent no-ops.
